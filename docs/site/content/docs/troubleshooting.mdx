## Agent won't start

- Open the terminal and run the agent's CLI manually. If it fails there, it's an auth or install problem in the CLI itself — not Orca.
- Make sure the CLI is on the `PATH` Orca sees (check [Settings → Agents](/docs/settings)).
- Try the **Restart** chip on the tab.

## Diff view looks wrong / stuck

- Click the refresh icon on the diff toolbar — Orca re-reads the worktree.
- External `git` operations (rebase, reset) can land between refreshes.

## Worktree creation fails

- The start-from ref may not be fetched. Open a terminal in the repo and run `git fetch origin`.
- The target directory may already have a worktree for that branch — delete it or pick a new branch name.

## Orca CLI says "command not found"

Register the CLI under [Settings → General → Orca CLI](/docs/settings). On macOS it installs a shim into `~/.local/bin`; make sure that's on your shell's `PATH`.

## SSH connects but remote terminals fail

- Confirm the remote has Node and network access for the first-time relay install.
- On Linux, install a C/C++ toolchain if terminals never spawn: make, g++/clang++, python3 (see [SSH worktrees](/docs/ssh)).
- Reconnect after installing tools so Orca can reinstall native modules.

## SSH works for files but not “Download Folder”

Folder download needs recursive SFTP transfer. File download may still work on system-SSH-only connections. Use a terminal `tar`/`scp` as a fallback.

## “Open in VS Code” is disabled or Local only

- Use an SSH worktree (not a Remote Orca Server active runtime).
- Set the Open-in command to VS Code / Insiders, not Cursor or a multi-arg shell command.
- Refresh SSH targets if the host was removed.

## Kerberos login fails

- Ensure `klist` shows a valid ticket for the host realm.
- Confirm `GSSAPIAuthentication yes` for that Host in OpenSSH config, then re-import or re-test the target in Settings → SSH.

## Browser says `browser_no_tab`

No tab is open in the current worktree. Open one with `orca tab create --url ...` or open the browser pane manually and navigate.

## Performance & memory

- Close worktrees you're not actively using. Each worktree keeps file watchers alive.
- Split layouts with many browser tabs are the biggest RAM users — close browsers you don't need.

## GitHub PR panel / checks / Tasks errors

Rate limits, bad `gh` auth, missing scopes, and repo access issues all show up in Source Control and the PR Checks panel. See **[Troubleshooting GitHub errors](/docs/github-errors)** for the full matrix (including why **GitHub API Budget** in Settings can look fine while REST is still blocked).

Quick checks:

```bash
gh auth status -h github.com
gh api user
gh api rate_limit --jq '.resources.core'
```

## Logs

**Help → Open Logs** opens the directory with Orca's logs. Attach these when filing a bug.

## Deep diagnostics & SRE

When the app itself is the suspect — wedged UI, terminals that never spawn, an SSH worktree that
will not connect — work outward from Orca's own on-disk evidence. Agents can load the full
procedure as a skill:

```bash
orca skills install --skill orca-diagnostics
```

See the [skills registry](/docs/cli/skills) for install scope and agent targeting.

Everything below lives in the [logs directory](#logs): `~/Library/Application Support/Orca/logs/`
on macOS, `~/.config/Orca/logs/` on Linux, `%APPDATA%\Orca\logs\` on Windows. A headless host
writes under `<data-root>/logs/` instead.

### Internal trace (`main.trace.ndjson`)

The main process writes one JSON object per line to `main.trace.ndjson`, synchronously, so the
last records survive a crash. Rotation is size-based — `main.trace.ndjson` → `.1` → … → `.N`,
oldest deleted, 10 MB × 10 files by default — so read `.N` as oldest and the unsuffixed file as
newest. A headless `orcad` host writes `orcad.trace.ndjson` under its own name instead.

```bash
jq -c 'select(.status == "error" or .level == "error")' main.trace.ndjson
```

An unparseable final line is a torn write from a crash, not a corrupt file. A record too large for
the per-line cap is replaced by a marker naming it, so gaps are explicit.

**Help → Send Feedback** collects these files into a diagnostic bundle and shows an editable
preview before upload — prefer it to hand-copied excerpts. Setting `ORCA_DIAGNOSTICS_DISABLED=1`
is the privacy switch; it also stops `daemon.log` from being written at all.

### Detached daemon logs

Terminals are hosted by a detached daemon that outlives an app restart. It records lifecycle
events — never terminal I/O, never tokens — as NDJSON in `daemon.log`. Its runtime files sit in
`<userData>/daemon/`, versioned by wire protocol: `daemon-v<N>.sock`, `daemon-v<N>.pid` (JSON with
`pid`, `startedAtMs`, `appVersion`), and `daemon-v<N>.token` (mode `0600`). On Windows the
endpoint is the named pipe `\\?\pipe\orca-terminal-host-v<N>-<hash>`.

- PID file present and the process alive → the daemon is fine; look above it.
- PID file present and the process gone → it died without teardown; the replacement cold-restores
  scrollback by design.
- Repeated starts seconds apart → a crash loop. Orca stops respawning after 5 failed starts in 60
  seconds, and only an explicit restart clears that window.
- `.swap-…` / `.hold-…` files beside the PID or token file are claims in progress. Never delete
  them; a live one briefly holds the only copy of a real record.

### Zombie PTY sockets

A `daemon-v<N>.sock` left by a dead daemon occupies the endpoint name while serving nothing. Only
a connect probe tells the states apart — `test -S` cannot:

| Probe result                           | Verdict                                     |
| -------------------------------------- | ------------------------------------------- |
| Connects                               | A daemon is live. Leave it alone.           |
| `ECONNREFUSED`, or `ENOTSOCK` on macOS | Nothing can serve it; safe to replace.      |
| Path absent                            | Safe to publish.                            |
| Timeout, `EPERM`, anything else        | **Leave it alone** — no proof of death.     |

Orca replaces a proven-dead endpoint on its next launch, so restarting the app is the normal fix.
Remove the socket by hand only when the app cannot be restarted and the probe refused or found
nothing. Note that a dangling symlink still occupies the name while an existence check that
follows symlinks reports it absent.

### Stale SSH multiplex sockets

System-OpenSSH connections use a private ControlMaster directory: `$XDG_RUNTIME_DIR/orca-ssh/`
when that variable is an absolute path, otherwise `$TMPDIR/orca-ssh-<uid>/`. It is created `0700`
and re-validated every time — a directory, owned by your uid, with no group or other bits. If that
check fails, Orca runs without multiplexing. Socket names are a digest of the target, the freshly
resolved `ssh -G` config, and whether the session is Kerberos-only, so a route or auth change never
reuses the wrong master.

A stale master shows up as system SSH exiting `255` with a mux client error while plain `ssh` to
the host works. Orca already recovers: it removes the socket and retries with ControlMaster
disabled for that session, so one occurrence is recovery, not a bug. Investigate when it repeats.

```bash
ls -la "${XDG_RUNTIME_DIR:-/tmp}/orca-ssh"* 2>/dev/null
ssh -O check -S <socket-path> <host>
ssh -O exit  -S <socket-path> <host>
```

Prefer `ssh -O exit` over `rm`: deleting a live master's socket leaves the process running with no
way to address it, and the next connection quietly starts a second master. Common directory-level
causes are a `/tmp/orca-ssh-<uid>` left owned by root after a `sudo` run, a group-writable
`XDG_RUNTIME_DIR`, or a tmpfs cleaner removing the directory mid-session.

### Point-in-time resource sweep

```bash
orca diagnostics memory --json
```

Runs the same host process sweep as the Resource Usage popover: app totals split across main,
renderer, and other processes, per-worktree terminal sessions, and host memory and load.

### Chrome DevTools Protocol (CDP) troubleshooting

When the UI is frozen, wedged, or a renderer process crashes without an error dialog, inspect the window state directly via CDP:

1. Launch Orca with a remote debugging port:
   ```bash
   orca --remote-debugging-port=9222
   ```
2. Query active targets and find the wedged window or webview:
   ```bash
   curl -s http://127.0.0.1:9222/json | jq ".[ ] | {title: .title, type: .type, id: .id}"
   ```
3. Evaluate renderer health and capture logs over the target WebSocket without revealing or focusing the window.

### Telemetry paths & offline state recovery

When Orca is closed or unresponsive, find its state and settings across platforms:

- **macOS**: `~/Library/Application Support/Orca/` (`logs/` and `orca-data.json`)
- **Linux**: `~/.config/Orca/` (`logs/` and `orca-data.json`)
- **Windows**: `%APPDATA%\Orca\` (`logs\` and `orca-data.json`)

#### Recovering from ghost tab reconciliation loops
If a tab flickers or repeatedly reopens after closing:
1. Quit Orca completely.
2. In `orca-data.json`, locate `"openFilesByWorktree"`.
3. Set the affected workspace ID entry to `[]` and clear `"activeFileIdByWorktree"`.
4. Relaunch Orca.

## Getting help & community support

### New to Orca?

Most "something is broken" reports on a fresh machine are setup gaps, not defects. Start with
**[Install](/docs/install)**, then **[Your first session](/docs/first-session)**, and check
**[Settings](/docs/settings)** for agent CLI paths. Running Orca on a remote or headless host is
covered in **[Remote servers](/docs/remote-servers)** and **[SSH worktrees](/docs/ssh)**.

### Let an agent set it up

Any coding agent — Claude Code, Codex, Cursor, Copilot — can install and verify Orca for you.
Click below or copy the prompt:

  <CopyPromptButton />
</div>

```text
Fetch and execute the appropriate instructions to set me up for Orca from
https://www.onorca.dev/docs/agent-setup/prompt.md
```

That file walks OS and architecture detection, desktop install on macOS, Windows, and Linux,
headless `orca serve` hosts, account and skill setup, a health-check pass, and the evidence to
collect when a step fails — so a broken install usually gets diagnosed before you open a thread.
It is plain markdown; read it yourself at
[/docs/agent-setup/prompt.md](https://www.onorca.dev/docs/agent-setup/prompt.md).

Pairing links, `sudo` for a `.deb`/`.rpm` install, and provider logins stay yours to approve.
Never let an agent paste a pairing URL, access link, or token into a public channel.

### Where to ask

- **[Discord](https://discord.gg/fzjDKHxv8Q)** — real-time help, setup questions, and "is this
  expected?" checks. The fastest channel for anything that is not yet a confirmed bug.
- **[GitHub Discussions](https://github.com/stablyai/orca/discussions)** — longer-form questions,
  workflow and configuration advice, and feature ideas worth a durable answer.
- **[GitHub Issues](https://github.com/stablyai/orca/issues)** — reproducible bugs and feature
  requests, with evidence attached.

### Reporting issues

- **Help → Send Feedback** (in-app) — paste or drag screenshots into the dialog, or pick image files; thumbnails show before you submit. Attach [logs](#logs) when the bug is hard to reproduce. Prefer this over a public issue when the logs contain host names or repo paths.

A report that can be acted on includes:

1. Orca version and platform (macOS / Linux / Windows, and whether the workspace is local, SSH, or a remote server).
2. What you did, and what happened instead.
3. The smallest reproduction you have found.
4. The relevant excerpt from [`main.trace.ndjson` or `daemon.log`](#logs) — redact file paths, repo names, host names, and tokens first.

If you are not sure whether it is a bug, run the [deep diagnostics](#deep-diagnostics--sre)
evidence sweep above or ask on Discord first — it is usually faster than waiting on issue triage.
